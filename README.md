# CI/CD labs: Item API

A minimal Java 21 / Spring Boot 4.1.1 REST service shared by two university CI/CD labs. Items are stored in memory and disappear when the application restarts. No database, authentication, or frontend is needed.

For the remaining account setup and lab demonstration steps, follow [Manual setup instructions](MANUAL_SETUP.md).

## Build, test, and run

Install JDK 21. The Maven wrapper downloads Maven on its first run.

```bash
./mvnw clean package
./mvnw test
./mvnw spring-boot:run
```

On Windows PowerShell use `.\mvnw.cmd` instead of `./mvnw`. You can also run the packaged application:

```bash
java -jar target/cicd-0.0.1-SNAPSHOT.jar
```

The service listens on port **8080**. Swagger UI: <http://localhost:8080/swagger-ui/index.html>. OpenAPI JSON: <http://localhost:8080/v3/api-docs>. All five endpoints appear automatically through [springdoc-openapi](https://springdoc.org/).

## REST API

| Method | Path | Success | Behavior |
| --- | --- | --- | --- |
| GET | `/api/items` | 200 | List items in ID order; initially `[]` |
| GET | `/api/items/{id}` | 200 | Fetch one item |
| POST | `/api/items` | 201 | Create with a generated ID and a `Location` header |
| PUT | `/api/items/{id}` | 200 | Replace the name and description; retain the ID |
| DELETE | `/api/items/{id}` | 204 | Delete an item; empty response body |

GET by ID, PUT, and DELETE return **404** for an unknown ID. POST/PUT accept JSON with a nonblank `name` and optional `description`; invalid input returns **400**. IDs are generated by the service and cannot be changed through request bodies.

```bash
curl -i -X POST http://localhost:8080/api/items -H 'Content-Type: application/json' -d '{"name":"Book","description":"Lab notes"}'
curl http://localhost:8080/api/items
curl http://localhost:8080/api/items/1
curl -i -X PUT http://localhost:8080/api/items/1 -H 'Content-Type: application/json' -d '{"name":"Updated book","description":"New notes"}'
curl -i -X DELETE http://localhost:8080/api/items/1
```

Use Swagger UI for the same demonstration without shell quoting. Tests cover the CRUD lifecycle, unique IDs, missing items, HTTP status codes, JSON responses, and request validation. Both pipelines run `clean verify`, which builds the application and runs the tests.

## Docker

Start Docker, then run:

```bash
docker build -t cicd-labs:latest .
docker run --rm -p 8080:8080 cicd-labs:latest
```

The multi-stage Dockerfile compiles with a Java 21 JDK and runs the executable JAR with a Java 21 JRE. Tests run in the CI build job; the Docker packaging stage skips them. The container exposes port 8080 and starts using `java -jar app.jar`.

## Lab 1: GitHub + Azure DevOps + Docker Hub

`azure-pipelines.yml` runs on pushes to `main`. It checks out GitHub source, selects Java 21, builds and tests with the Maven wrapper, publishes JUnit results, and uses `Docker@2` to build, tag, and push `latest` through a Docker Registry service connection.

Manual setup:

1. Push this project to GitHub. In Azure DevOps, create a YAML pipeline connected to that GitHub repository and select `/azure-pipelines.yml`.
2. Create a Docker Registry service connection for Docker Hub using your username and Docker Hub access token. Authorize the pipeline to use it.
3. Replace `REPLACE_WITH_DOCKERHUB_SERVICE_CONNECTION` in the YAML with that connection's name.
4. Create a Docker Hub repository and replace `REPLACE_WITH_DOCKERHUB_USERNAME/cicd-labs` with its `namespace/repository` name.
5. Enable access to Microsoft-hosted agents and push a change to `main`. Review test results and the Docker Hub tag after the run.

Keep credentials in the service connection. [Docker task reference](https://learn.microsoft.com/en-us/azure/devops/pipelines/tasks/reference/docker-v2?view=azure-pipelines).

## Lab 2: GitHub Actions + Docker Hub

`.github/workflows/ci.yml` runs on pushes to `main`, `feature/*`, and `bugfix/*`. A push changing only `docs/**` and/or `README.md` is ignored. The `build-n-test` job uses Java 21 and Maven. Only after it succeeds does `docker-pack-n-push` call `.github/workflows/docker.yml`.

The reusable workflow accepts `image`, `tag`, and `push` inputs plus optional Docker Hub secrets. On `main`, CI passes `push: true` and tag `latest`; the workflow logs in and pushes. On feature/bugfix branches, it builds with the commit SHA tag, saves `docker-image.tar`, and uploads an artifact named `docker-image-<commit SHA>`. Those branches need no Docker Hub credentials. Push steps also explicitly require the `main` branch.

In GitHub **Settings > Secrets and variables > Actions**, configure:

| Type | Name | Value |
| --- | --- | --- |
| Secret | `DOCKERHUB_USERNAME` | Your Docker Hub username |
| Secret | `DOCKERHUB_TOKEN` | A Docker Hub access token with push access |
| Variable | `DOCKERHUB_IMAGE` | Your Docker Hub `namespace/repository`, e.g. `your-username/cicd-labs` |

Create the Docker Hub repository before pushing. The local image fallback `cicd-labs` lets feature/bugfix builds work without configuration; main builds fail with a configuration message until the variable and secrets are set. No real credentials belong in repository files.

To use an image artifact, download it from the workflow run, extract the artifact ZIP, then run:

```bash
docker load --input docker-image.tar
docker run --rm -p 8080:8080 cicd-labs:<commit-sha>
```

If `DOCKERHUB_IMAGE` was configured, use that image name instead of `cicd-labs`.

## Verification limits

Local verification passed: Maven `clean verify` produced the executable JAR and ran eight tests with no failures. A live check of the packaged JAR verified CRUD responses, missing-item 404, Swagger UI, and all five operations in the OpenAPI document. All three pipeline YAML files parsed successfully.

The local Docker daemon was unavailable, so the Docker image was not built or run locally. The Dockerfile was reviewed for its build stages, JAR path, exposed port, and startup command.

GitHub Actions, Azure DevOps, and Docker Hub publication require the repository/account setup above. Local compilation and tests do not prove a remote pipeline or registry push succeeded. Docker image builds and container checks require a running Docker daemon.
